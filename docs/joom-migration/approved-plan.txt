Configure exact Spark4.2.1/Scala2.13.18 and Delta4.4.1, minimal GCP ADC/planning adaptations; use stock registry DataFusion55.2.0 crates with the current target lock's Arrow/Parquet59.3.2. Obtain baseline Comet/Delta/ANSI fixture results before vendoring.

G01.2 Pristine vendor in a separate commit
Import the published standalone datafusion-physical-plan55.2.0 with provenance/checksum/license in a separate mechanical commit. Do not port the old Cargo55.1 or inherit Comet workspace.version1.2.0; the crate name/version remains datafusion-physical-plan55.2.0.
Validation: Sources match pristine55.2; no Joom algorithmic diff.

G01.3 Connect vendor and a separate test target
Configure the root patch and include the vendored crate in the native workspace with an explicit unit/regression test target. Use shared native/Cargo.lock/root patch; membership alone or cargo test --manifest-path is insufficient.
Validation: Verify the resolved graph: release Comet and vendor tests use a single local physical-plan55.2.0 identity, runtime DF55.2/Arrow59.3.2. Unit-test dev dependencies may add lock entries, but must not arbitrarily update the runtime graph. CI explicitly selects the package; Comet-only default-members do not imply running vendor unit tests.

G01.4 Repeat validation and release tooling
Repeat baseline checks after replacing the registry crate with a pristine path crate. Prepare build-release.sh/publish-jfrog.sh, multiarch packaging/provenance; separately verify upstream native-library reload.
Validation: Compare before/after-vendoring results and plans, explicitly run vendor unit/regression tests and Comet/Delta suites, verify libcomet packaging/GLIBC/Scala. G01 produces an internal RC1; the full Joom capability set is not yet ported.

Joom algorithms in the DataFusion vendor begin only in G03 (sort), G04 (aggregates) and G05 (SMJ). G01 keeps the vendor pristine.

QUALITY
The 40 old packages remain an internal checklist of scope, dependencies and checks, rather than 40 PRs.
Each large PR has atomic commits/meaningful substeps, with checks after them rather than a single test run at the end.
A single enormous squash commit without reviewable structure is not proposed; retain informative history.
During review, clearly separate mechanical vendor import from manual changes; provenance/hashes are recorded in the register.
Overall CI/feature/runtime/ANSI gates are not reduced. Fix or restrict a known unsafe-result path before production.
If a package cannot objectively be reviewed well at this size, do not combine further merely to meet the limit; show the concrete diff and propose a split within the reserve.
Do not leave C01/C02/C03/Q01 as 4 hidden extra PRs: their owners are explicitly assigned in the table.
Qualify G09 after all of G03-G08. Groups follow the main sequential order; parallel implementation is not required.

BENEFITS AND COSTS OF CONSOLIDATION
Fewer CI/rebase/merge cycles without losing scope.
Removes artificial temporary boundaries between BoundaryFormats and the cost model.
Integrates a complete related capability together with regressions.
Review is larger and isolating a bug inside a block is harder; therefore atomic commits/substeps are needed.
G01 includes a large mechanical vendor import; G04/G06/G07 may produce substantial diffs. Assess their reviewability from the actual patch, not a promise.
